# 资产空间分层方案（个人资产 / 应用资产 / 服务资产）

本文档说明 Warehouse 当前已经落地的资产空间分层设计。登录后的资产管理界面和 WebDAV/S3 目录将用户资产分成三类并独立管理：

- 个人资产（用户主动上传/管理）
- 应用资产（DApp/前端应用写入，按 appId 隔离）
- 服务资产（后台服务集成、定时任务和服务端自动化产物）

## 文档边界

本文主要回答“用户登录后资产目录怎么分层、目录如何命名、UI 入口如何组织、UCAN 与路径空间如何对齐”，并记录当前实现边界和持续验收要求。

以下内容不在本文重复展开：

- 公开分享、站内共享及其演进方案：见 [共享方案.md](./共享方案.md)
- 回收站当前实现：见 [仓库架构V1.md](./仓库架构V1.md)

## 1. 设计目标

1. 登录后提供三个明确入口，避免“个人文件”“应用文件”和“服务产物”混在同一层。
2. 保持 WebDAV 协议兼容，Finder/Windows/rclone 等第三方客户端可直接访问。
3. 与 UCAN app scope 对齐，确保第三方 DApp 仅可访问自己的应用目录。
4. 对现有数据和现有客户端保持平滑迁移。

## 2. 目录命名与结构

## 2.1 命名结论

- 个人资产目录命名为：`personal`
- 应用资产根目录命名为：`apps`（保持现有约定）
- 服务资产根目录命名为：`services`

命名理由：

- `personal` 语义直接，便于前后端、文档和第三方工具统一理解。
- 不使用中文目录名，避免不同客户端编码/展示差异。
- 与 `apps` 平行，结构清晰，服务端集成产物不再挤占 DApp/UCAN 目录。

## 2.2 用户根目录结构

每个用户注册成功后，初始化其独立根目录：

```text
/<user_root>/
  personal/                 # 个人资产空间（默认入口）
  apps/                     # 应用资产空间（应用隔离根）
    <appId-a>/
    <appId-b>/
  services/                 # 服务资产空间（后台服务产物）
    <service-name>/
```

说明：

- `apps/<appId>/` 由 DApp 首次写入时按需创建（或由服务端预创建）。
- `appId` 推荐使用域名主机部分，如 `dapp.example.com`。
- `services/<service-name>/` 可由用户或后台服务按约定创建；当前没有独立的 service principal 身份模型。

## 3. 登录后 UI 入口

登录后的资产导航提供三个空间入口：

- `个人资产` -> 对应路径 `/personal`
- `应用资产` -> 对应路径 `/apps`
- `服务资产` -> 对应路径 `/services`

当前交互规则：

1. 登录成功默认进入 `个人资产`（`/personal`），符合普通用户心智。
2. 切换到 `应用资产` 后先展示应用列表（`/apps` 下一级目录），点击进入某个 app 子目录。
3. 面包屑中显式显示空间类型，例如：`个人资产 / 合同 / xx.pdf`、`应用资产 / dapp.example.com / data.json`、`服务资产 / reporting / daily.json`。

## 4. 权限模型与隔离边界

## 4.1 个人资产访问

- 用户通过密码/JWT 登录后，可按其自身权限访问 `personal` 与其他允许路径。
- UI 层默认把日常上传、移动、删除操作落在 `personal`。

## 4.2 应用资产访问（UCAN）

UCAN 方式使用 app scope：

- 服务端配置：`required_resource=app:*`，`required_action=read,write`（或只读 `read`）。
- DApp cap：`resource=app:<appId>`。
- 请求路径必须在 `/apps/<appId>/...`。

这样可以保证：

- DApp A 不能访问 DApp B 的目录。
- DApp 默认也不能访问 `personal`（除非另行定义并显式授权）。

## 4.3 服务资产访问

- 服务资产属于当前用户目录，沿用现有 JWT、WebDAV 凭证和 S3 凭证授权。
- `services` 不纳入 UCAN app scope；DApp 仍只能通过 `/apps/<appId>/...` 访问自己的应用目录。
- 后续如要支持真正的后台服务身份，再单独引入 service principal、服务级配额和更细的审计模型。

## 5. WebDAV 第三方客户端兼容性

第三方 WebDAV 客户端挂载后看到用户根目录下的 `personal/`、`apps/` 与 `services/` 三个主目录即可，无需协议改造。

推荐实践：

1. 对普通用户文档提示“日常文件放 `personal/`”。
2. 对开发者文档提示“DApp/UCAN 应用数据仅写入 `apps/<appId>/`”。
3. 对后台服务文档提示“服务端自动化产物写入 `services/<service-name>/`”。
4. 保持根路径可访问，避免强制路径重写导致客户端 301/404 问题。

## 6. 注册初始化与存量兼容

## 6.1 新用户

注册成功后自动创建：

- `/<user_root>/personal`
- `/<user_root>/apps`
- `/<user_root>/services`

## 6.2 存量用户

存量用户登录时会幂等补齐缺失的空间目录。历史根目录数据如需归入 `personal/`，应通过经过验证的迁移流程处理：

1. 创建缺失目录：`personal/`、`apps/`、`services/`。
2. 把用户根目录下的“业务文件”迁移到 `personal/`。
3. 保留 `apps/` 原有结构不变。
4. 提供一次性迁移日志与回滚窗口。

迁移时至少应排除：

- `apps`
- `services`
- 系统回收/元数据目录（按现网实现）

## 7. 空间元信息 API 与前端

当前通过“资产空间元信息”接口向前端提供空间定义，降低前端硬编码路径的维护成本：

- `GET /api/v1/public/assets/spaces`

示例响应：

```json
{
  "code": 0,
  "data": {
    "defaultSpace": "personal",
    "spaces": [
      { "key": "personal", "name": "个人资产", "path": "/personal" },
      { "key": "apps", "name": "应用资产", "path": "/apps" },
      { "key": "services", "name": "服务资产", "path": "/services" }
    ]
  }
}
```

前端基于该响应渲染空间入口，并保留 `personal`、`apps`、`services` 的本地降级定义，避免接口异常时阻断基本文件访问。

## 8. 当前完成状态与持续验收

当前已经完成：

- 新用户注册时初始化 `personal/`、`apps/`、`services/`，老用户登录时幂等补齐。
- `GET /api/v1/public/assets/spaces` 返回默认空间和三类空间元信息。
- 前端展示个人资产、应用资产和服务资产入口，默认空间为 `personal`。
- UCAN `app:<appId>` 限制在 `/apps/<appId>/...`，不开放 `personal` 或 `services`。
- WebDAV 和 S3 复用同一套用户空间目录与权限边界。

后续修改资产空间相关代码时，应持续验证：

- 新老用户均能看到三个空间目录，重复初始化不会报错或覆盖数据。
- 三个空间可正常完成列表、上传、下载、移动、删除和回收站相关操作。
- UCAN 无法跨应用目录访问，也无法访问个人资产或服务资产。
- WebDAV、S3 和 Web 页面看到的数据保持一致。
- `GET /api/v1/public/assets/spaces` 与 OpenAPI、前端展示名称及默认空间保持一致。
