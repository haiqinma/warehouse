# 仓库架构 V2

本文描述 Warehouse V2 已经实现并进入冻结的架构事实。V1 基础架构见 [仓库架构V1.md](./仓库架构V1.md)，V2 之后的正式多副本、状态外置和自动编排见 [仓库架构V3.md](./仓库架构V3.md)。

## 版本定位

V2 将 Warehouse 从“具备基础 active / standby 复制的文件服务”收敛为“可观察、可恢复、可运维的社区资产数据面”。

V2 保持以下边界：

- Warehouse 负责文件/对象、资产空间、权限、凭证、配额、checksum、WebDAV/S3/HTTP API 和复制。
- Knowledge 负责 Agent Run、Context Manifest、Service Principal、Artifact Provenance 等上层 AI/Agent 业务语义。
- 高可用形态仍是 `1 active + N standby`，不把 standby 变成可任意接流量的无状态副本。
- failover / promote 依然由运维按 SOP 人工执行，不在 V2 内自动切换。

## Knowledge 资产数据面

V2 在现有资产空间上增加了不携带 Knowledge 业务语义的 HTTP 对象接口：

- `GET /api/v1/public/assets/object`：返回单对象 metadata 和 SHA-256。
- `GET/HEAD /api/v1/public/assets/object/content`：读取对象内容或响应头。
- `PUT /api/v1/public/assets/object/content`：写入对象，支持 SHA-256 校验。
- `GET /api/v1/public/assets/objects`：按 prefix / delimiter 列出对象和公共前缀。

写入复用 `ObjectService`，仍经过 quota、metadata 和 replication mutation recorder。UCAN app scope 会限制 `/apps/<appId>` 的读写，不允许 app-scoped 凭证越界访问其他 app 或 `/services`。

Warehouse 不解析 manifest、artifact 或 feedback 的业务语义；它们作为普通资产保存。路径建议、错误语义和调用示例见 [Knowledge资产接入方案.md](./Knowledge资产接入方案.md)。

## Reconcile 调度与自愈

active 会在启动时执行 reconcile 检查，之后周期性扫描当前有效 standby assignment。

已实现的状态行为：

- `pending` assignment 可自动进入 reconcile。
- 同一 source / target / generation 的 running job 会在重启后续跑，不重复扫描创建新 job。
- reconcile 完成后向 standby 写入 bootstrap outbox baseline，再将 assignment 切换到 `replicating`。
- 失败会记录 job/assignment last error、failure count 和 next retry time。
- 连续失败达到 `replication.reconcile_auto_pause_failures` 后 assignment 进入 `paused`，需要运维显式 `resume`。
- generation mismatch、offset baseline 缺失和 sequence conflict 保持显式错误，不绕过 fence 继续 apply。

scanner 只处理稳定资产，跳过 `.recycle/`、`.warehouse-uploads/`、`.s3-multipart/`、写入/复制临时文件和 apps sync 运行态对象。详细边界见 [多副本方案.md](./多副本方案.md#v2-reconcile-自愈方案)。

## 复制观测与部署告警

V2 的观测出口是 internal replication status、`warehouse ha status`、assignment CLI 和结构化日志。它们能提供：

- outbox pending / failed / last dispatched 与 last error。
- source / target、assignment state、generation、lease 和 `leaseExpired`。
- offset generation、last applied outbox ID 和复制 lag 解释。
- reconcile job status、scanned/pending items、last error。
- assignment failure count、next retry time 和 last reconcile job ID。

部署侧告警按 [部署手册.md](./部署手册.md) 的稳定字段判定：`error|paused`、lease/心跳过期、failed events 持续存在、pending 长期不下降、reconcile 长期 running 或 offset 长期落后。

V2 不内置 Prometheus `/metrics` 和预置 alert rules；这些属于 V2.x / V3 的运维平台化能力。

## 多 Standby Reconcile 资源保护

V2 在 active 进程内实现两层基础保护：

- `replication.reconcile_max_concurrency`：限制同时执行的 reconcile 数量，默认 `1`。
- `replication.reconcile_bandwidth_limit_bytes_per_second`：限制所有 reconcile 共享的全局出站速率，默认 `0` 表示不限速。

自动 sweep 和手工 `ha reconcile start` 使用同一个并发闸门，手工命令不能绕过保护。限速只作用于历史 reconcile batch，不限制正常 WebDAV/S3/HTTP 写入和 outbox 增量复制。

V2 没有实现按 standby 独立的带宽配额或动态公平调度；需要更精细的单 standby 隔离时，由 V2.x / V3 结合指标和部署层 QoS 继续完成。

## Generation 生命周期

V2 已实现“当前代际强保护、明细短保留、摘要长保留”：

| 数据 | 默认保留 | 实现边界 |
| --- | --- | --- |
| `replication_reconcile_items` | 7 天 | 只清理已结束 job 的 item，running job 全部保留 |
| `replication_reconcile_jobs` | 30 天 | 保留 running job、assignment last job 和每个 source/target/generation 最新 job |
| `replication_outbox` | 7 天 | 只清理不再属于当前 assignment generation 的历史事件 |
| `replication_offsets` | 不自动删除 | 保留作为切换和故障排查摘要 |
| `cluster_replication_assignments` | 不自动删除 | 保留控制面状态，归档/裁剪放到 V3 |

自动 cleaner 只在 replication-enabled active 节点运行，启动时执行一轮，之后按配置周期执行。人工入口为：

```bash
warehouse ha cleanup history -c config.yaml --dry-run
warehouse ha cleanup history -c config.yaml
```

`--dry-run` 使用只读事务统计命中数量；实际执行使用事务删除并返回 item/job/outbox 计数。命令只接受 active 配置，不提供绕过 generation 保护的 `--force`。

## Quota 运维基础

V2 保持用户级 quota 模型，增加了：

- active 节点后台自动对账。
- `quota.auto_reconcile_batch_size` 和 `quota.auto_reconcile_batch_pause`，用于分批处理和批间让出资源。
- checked/repaired/failed 计数、用户失败日志和 near-limit/over-quota 风险日志。
- 管理端用户列表的 `quota_status` 和 `quota_usage_percent`。
- WebDAV 目录 COPY 按源目录相对文件逐个抵扣目标同路径文件，写前校验和写后记账复用同一 delta。

当前实现是“一次加载用户列表后分批处理”，不是 PostgreSQL cursor 分页。数据库分页、持久失败状态和更完整的 quota 产品化属于 V2.x / V3。

## WebDAV 系统对象生命周期

apps 下受精确命名规则约束的 `backup.__sync_*` 对象被定义为 sync 运行态对象。它们的已实现生命周期是：

- 有该路径 DELETE 权限的调用方通过 WebDAV `DELETE` 删除时直接硬删除，不进入用户回收站。
- 硬删除后清理相关分享引用，并按实际删除大小释放 `used_space`。
- mutation recorder 和 reconcile scanner 共用同一识别规则，不把运行态对象带入 standby。
- 历史误入 `.recycle` 的记录通过以下命令预览和清理：

```bash
warehouse recycle clean-sync-artifacts -c config.yaml --dry-run
warehouse recycle clean-sync-artifacts -c config.yaml
```

V2 没有新增独立 internal hard-delete API；硬删除边界由现有 WebDAV 权限与精确系统对象路径规则共同约束。普通用户文件的 `DELETE` 仍进入回收站。

## 人工切换边界

V2 不提供自动 promote / failover。[部署手册.md](./部署手册.md#7-人工切换-sop) 是唯一人工切换入口，已固化：

1. 切换前检查 assignment、lease、outbox/offset lag、reconcile 和 readiness。
2. 从 LB 摘除并停止/网络隔离旧 active。
3. 将目标 standby 以其自身 node ID 提升为新 active。
4. 新 active 接受写入后，旧 active 必须以 standby 身份重新 reconcile，不得直接回切。
5. 回切必须再次经过完整隔离和提升流程。

readiness 只表示进程、PostgreSQL 和本地目录可用，不表示 standby 已追平 active。

## 已验证范围

V2 冻结提交已通过以下自动化门禁：

```text
go test ./...
npm run openapi:lint
npm run openapi:generate
npm run build:test
git diff --check
```

代码级测试覆盖 Knowledge 对象读写/checksum/UCAN scope、reconcile 状态机和并发闸门、generation cleanup preview/执行、quota 分批和 COPY delta、sync artifact 识别与历史清理。

真实 active + standby / active + 2 standby 的中断恢复、限流效果和人工 failover 属于发布环境运维验收，不在本文中声称已完成。

## V2 之后

以下内容未进入 V2 实现，统一由 [仓库架构V3.md](./仓库架构V3.md) 或 V2.x hardening 承接：

- 正式无状态多副本、共享文件内容和完整状态外置。
- 自动 failover / promote / rebalance / drain / release 编排。
- Prometheus `/metrics`、预置 alert rules 和统一运维控制面。
- 按 standby 独立带宽、动态公平调度和大文件流式 reconcile。
- quota 数据库游标分页、持久失败状态、自助扩容、计费和多主体额度。
- 独立 internal hard-delete API 与更完整的资产访问审计。
- Agent Run、Context Manifest、Service Principal、Artifact Provenance 控制面。
