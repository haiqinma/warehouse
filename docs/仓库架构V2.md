# 仓库架构 V2

本文只记录 Warehouse 下一阶段尚未完整实现的架构目标。已经实现的当前基线见 [仓库架构V1.md](./仓库架构V1.md)。

## 版本规则

- `仓库架构V1.md`：当前已经实现并可以运行的架构事实。
- `仓库架构V2.md`：下一阶段准备实现的架构目标和验收口径。
- 后续继续按 `仓库架构V3.md`、`仓库架构V4.md` 递增，不在一个总览文档里混写所有时代。

## V2 目标

| 方向 | V2 目标 |
| --- | --- |
| 高可用 | 在 V1 `1 active + N standby` 基础上补齐更完整的自愈、观测和人工切换闭环 |
| 多副本 | 明确从单活复制走向正式多副本的约束和阶段 |
| 运维 | 降低复制漂移、故障切换和升级时的人肉判断成本 |
| 额度 | 在当前用户级 quota 基线上补齐观测、性能和产品化能力 |
| 产品边界 | Warehouse 保持通用存储底座，上层 AI/Agent 语义由 Knowledge 承接 |

## V2 候选能力

### 多副本增强

- 自动 failover / promote 的前置检查。
- 更完整的周期性 reconcile 和漂移修复。
- standby 落后、失败、恢复后的自动调度。
- 多 standby 下的 reconcile 并发控制和限流。
- 复制 lag、last error、assignment state 的告警规则。

详细设计见 [多副本方案.md](./多副本方案.md)。

### 状态外置

当前 WebDAV 锁、challenge、邮箱验证码等临时状态仍有进程内依赖。V2 需要评估：

- WebDAV lock 外置。
- 钱包 challenge 外置。
- 邮箱验证码外置。
- 上传会话、分片会话等未来临时状态统一外置。

### 正式多副本方向

正式多副本不应依赖“每个副本都有自己的本地文件目录并同时接用户写流量”。推荐方向是：

- 共享 PostgreSQL。
- 共享 POSIX 文件存储，或进一步抽象到对象存储。
- 外置临时状态层。
- 2~N 个应用副本可滚动发布。
- LB 可转发到任意健康副本。

### AI 原生边界

当前决策是：

- Warehouse 继续负责文件/对象、权限、凭证、配额、checksum、WebDAV/S3 和复制。
- Knowledge 负责 Agent Run、Context Manifest、Service Principal、Artifact Provenance 等上层业务语义。
- Warehouse 为 Knowledge 保存原始资产、manifest 投影和 artifact 文件。
- Warehouse 的 V2 重点是把服务资产、协议接入、权限、checksum、稳定路径和回写反馈做成可被 Knowledge 可靠依赖的标准化能力，而不是在 Warehouse 内实现 Agent Run 控制面。

产品定位的长篇推导和参考资料见 [AI原生存储产品定位决策分析.md](./AI原生存储产品定位决策分析.md)。V2 只吸收其中已经收敛的工程边界，不重复维护市场分析和研究材料。

### 额度管理增强

当前 quota 基线见 [额度管理方案.md](./额度管理方案.md)。V2 继续补齐：

- 目录级 `COPY` / 目录树复制的高性能 quota 估算。
- quota 对账分片扫描、限速和观测指标。
- 使用率预警，例如 80% 提醒、90% 强提醒、100% 拒绝新增写入。
- 管理端额度视图，支持按使用率、已超额、接近上限筛选用户。
- 用户自助申请扩容，审批仍由管理员决定。
- 更完整的逻辑文件元数据表，用于更快的 quota rebuild、更精确的回收站统计和后续多主体额度。
- 高并发上传下的额度 reservation：预占用、成功提交、失败回滚。

## V2 验收口径

V2 不能只写成路线图，需要能被验收：

- standby 中断后恢复，能自动追上或明确进入可操作的失败状态。
- 复制 lag、assignment、reconcile、last error 能被稳定观察。
- 多 standby 同时补历史时，不明显拖垮 active 正常服务。
- quota 对账、预警、管理端视图和高成本扫描有明确的运维观察与限流手段。
- Warehouse 能稳定作为 Knowledge 的数据源，并能接收 Knowledge 生成的 manifest 投影、artifact 和反馈资产。
- 故障切换前有清晰检查项，切换后有清晰回滚路径。
- 文档和部署手册只维护一套运维命令。

## V2 执行清单

### 优先推进

#### reconcile 调度与自愈

目标是在已具备 startup reconcile、周期性 reconcile sweep 和 running reconcile job 启动恢复的基础上，补齐更完整的历史补齐自愈能力。

- reconcile 失败后的细粒度节流、失败分类与分级重试策略。
- reconcile 自动暂停阈值与恢复路径。
- reconcile 差异比较与跳过逻辑，减少无效传输。

验收标准：

- standby 中断、重启、长时间落后后，重新上线能够自动恢复到一致状态。
- 失败后的重试、退避、暂停、恢复路径可预测、可观察、可运维介入。

#### 多 standby 下的 reconcile 并发与限流

目标是在已经支持 `1 active -> N standby` 的基础上，补齐并发控制、带宽限制和资源保护。

- 多 standby 下的 reconcile 并发数控制。
- 单 standby 与全局带宽限流。
- active 本机资源保护策略，避免 reconcile 抢占正常写流量。
- 单个 standby 异常时的资源隔离与退避策略。

验收标准：

- 多个 standby 同时补历史时，不会明显拖垮 active 的正常服务。
- 单个 standby 的慢或失败，不会放大成全局抖动。

### 近期补齐

#### 观测与告警

- 复制 lag、failed events、reconcile pending items、assignment lease 状态指标。
- standby 复制链路中 generation mismatch、sequence conflict、assignment 失效等关键错误的结构化日志。
- active / standby 心跳过期告警。
- reconcile 失败与长期未完成告警。
- `ha status` 输出补充 generation / assignment 状态解释字段。

验收标准：

- 不看数据库明细，也能通过日志、状态接口、指标快速定位复制链路问题。

#### WebDAV 系统对象生命周期治理

- 设计受限硬删除接口，供 chat 等内部应用显式清理同步内部对象。
- 为硬删除接口补充能力校验或内部认证边界，避免普通客户端绕过回收站。
- 梳理并固化可硬删除的系统对象范围，减少散落的路径特判。
- 增加历史 `.recycle` 中 `__sync_*` 系统对象的识别与清理脚本。

验收标准：

- 用户文件删除仍默认进入回收站。
- 系统同步对象具备受控、可审计、不会污染回收站的清理路径。

#### 旧 generation 数据清理与归档

- 为 `replication_outbox` 增加旧 generation 清理策略。
- 为 `replication_reconcile_jobs` / `replication_reconcile_items` 增加保留期与清理策略。
- 明确 `replication_offsets` 在 assignment 释放或切换后的保留策略。
- 明确 `cluster_replication_assignments` 的 released / expired 记录是否归档或裁剪。
- 设计人工触发与自动清理两种方式。

验收标准：

- 长期运行后数据库不会因为历史 generation 累积而无限膨胀。

#### 额度管理增强

- 目录级 `COPY` / 目录树复制的高性能 quota 估算，避免大目录复制时反复递归扫描。
- quota 对账任务分片扫描、限速、失败记录和结构化告警。
- 管理端额度视图，支持识别接近上限、已超额和统计可能漂移的用户。
- 使用率预警与用户自助扩容申请入口，扩容审批仍由管理员负责。
- 逻辑文件元数据表，为更快的 quota rebuild、更精确的回收站统计和后续多主体额度打基础。
- 高并发上传下的 reservation 状态机，包括预占用、成功提交、失败释放。

验收标准：

- 大目录复制和大规模对账不会拖垮 active 正常读写。
- 管理员不查数据库也能定位用户超额、统计漂移和对账失败。
- quota 仍只在 active 对外写入口判定，standby 不因副本同步重复拒绝或重复计量。

#### AI 原生存储支撑能力

- 固化 `personal` / `apps` / `services` 三类资产空间作为 Knowledge 的数据源入口。
- 为 Knowledge 写回的 manifest 投影、artifact 和反馈资产提供稳定路径、checksum、权限和审计口径。
- 明确 Warehouse 只保存文件/对象和可验证元数据，不承接 Agent Run、Context Manifest、Service Principal、Artifact Provenance 的业务控制面。
- 在 WebDAV/S3/HTTP API 中保持服务资产可读写、可授权、可追踪，方便 Knowledge 和第三方服务接入。

验收标准：

- Knowledge 可以稳定读取 Warehouse 原始资产，并把处理结果写回 Warehouse。
- 用户能在 Warehouse 中看到 Knowledge 生成或回写的资产，但不需要 Warehouse 理解完整 Agent Run 语义。
- WebDAV/S3 兼容入口不因 AI 原生支撑能力变更而破坏。

### 后续增强

- 多 standby 调度与编排：补齐 rebalance / drain / release 的编排规则与保护策略，以及 failover / promote / 回切 SOP 与自动化边界。
- 运维 CLI 扩展：增强 `warehouse ha assignments status`，补齐 `rebalance`、`promote`、reconcile / bootstrap / assignment 的统一观察入口。
- 大文件与性能优化：支持大文件流式 reconcile、复制批量大小自适应、带宽限流与背压、单文件重复校验与跳过优化。

## V2 建议执行顺序

1. 先补 reconcile 调度与自愈。
2. 再补多 standby 下的并发与限流。
3. 随后补观测、告警、generation 生命周期管理和 quota 运维增强。
4. 同步固化 Warehouse 支撑 Knowledge 的数据源与反馈资产边界。
5. 最后推进多 standby 调度、编排自动化与运维 CLI 扩展。
