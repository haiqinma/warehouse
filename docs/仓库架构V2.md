# 仓库架构 V2

本文只记录 Warehouse 下一阶段必须优先落地的架构目标。已经实现的当前基线见 [仓库架构V1.md](./仓库架构V1.md)，更长期的平台化能力见 [仓库架构V3.md](./仓库架构V3.md)。

## 版本规则

- `仓库架构V1.md`：当前已经实现并可以运行的架构事实。
- `仓库架构V2.md`：下一阶段必须优先落地的能力，目标是证明 Warehouse 可以作为可靠的社区资产底座。
- `仓库架构V3.md`：V2 稳定后再推进的平台化能力，目标是正式多副本、状态外置、自动编排和更完整的产品化治理。
- 后续继续按 `仓库架构V4.md` 递增，不在一个总览文档里混写所有时代。

## V2 定位

V2 不追求“大而全的下一代架构”。V2 的核心目标是：

> 证明 Warehouse 是社区生态中可靠的资产数据面，可以稳定服务人、应用、服务和 Knowledge。

V2 保留的工作必须同时满足：

1. 直接提升当前生产稳定性、可恢复性或可观测性。
2. 直接支撑 Warehouse 作为 Knowledge 数据源和反馈资产回写层。
3. 能在当前 `1 active + N standby` 基线上落地，不要求正式无状态多副本改造。
4. 不把 Agent Run、Context Manifest、Service Principal、Artifact Provenance 等上层业务语义放进 Warehouse。

## V2 目标

| 方向 | V2 目标 |
| --- | --- |
| 产品边界 | 固化 Warehouse 在社区生态中的资产数据面定位，上层 AI/Agent 语义由 Knowledge 承接 |
| Knowledge 接入 | 标准化原始资产读取、manifest 投影、artifact 和反馈资产回写的路径、权限、checksum 与审计口径 |
| 高可用 | 在 V1 `1 active + N standby` 基础上补齐 reconcile 自愈、观测、限流和 generation 生命周期 |
| 运维 | 降低复制漂移、对账漂移、故障定位和人工恢复成本 |
| 额度 | 在当前用户级 quota 基线上补齐必要的对账观测、限速和管理视图 |
| 系统对象治理 | 为内部同步对象、chat 等系统对象提供受控清理路径，避免污染用户回收站 |

## V2 必做能力

### Knowledge 数据源与反馈资产边界

当前决策是：

- Warehouse 继续负责文件/对象、权限、凭证、配额、checksum、WebDAV/S3、HTTP API 和复制。
- Knowledge 负责 Agent Run、Context Manifest、Service Principal、Artifact Provenance 等上层业务语义。
- Warehouse 为 Knowledge 保存原始资产、manifest 投影、artifact 文件和反馈资产。

V2 需要标准化：

- `personal` / `apps` / `services` 三类资产空间作为 Knowledge 数据源入口。
- Knowledge 读取 Warehouse 原始资产时的路径、权限、checksum 和错误语义。
- Knowledge 写回 manifest 投影、artifact 和反馈资产时的目标路径、归属用户、权限与审计口径。
- WebDAV/S3/HTTP API 中服务资产的读写一致性，确保第三方服务和 Knowledge 都能接入。

验收标准：

- Knowledge 可以稳定读取 Warehouse 原始资产，并把处理结果写回 Warehouse。
- 用户能在 Warehouse 中看到 Knowledge 生成或回写的资产，但 Warehouse 不需要理解完整 Agent Run 语义。
- WebDAV/S3 兼容入口不因 AI 原生支撑能力变更而破坏。

产品定位的长篇推导和参考资料见 [AI原生存储产品定位决策分析.md](./AI原生存储产品定位决策分析.md)。社区级职责边界见 [社区产品关系与开发边界.md](../../books/yeying/社区产品关系与开发边界.md)。

### Reconcile 调度与自愈

目标是在已具备 startup reconcile、周期性 reconcile sweep 和 running reconcile job 启动恢复的基础上，补齐更完整的历史补齐自愈能力。

- reconcile 失败后的细粒度节流、失败分类与分级重试策略。
- reconcile 自动暂停阈值与恢复路径。
- reconcile 差异比较与跳过逻辑，减少无效传输。
- standby 中断、重启、长时间落后后的恢复路径。

验收标准：

- standby 重新上线后能够自动追上，或进入明确、可操作的失败状态。
- 失败后的重试、退避、暂停、恢复路径可预测、可观察、可运维介入。

### 复制观测与告警

V2 必须先让复制链路可观察，再考虑自动化编排。

- 复制 lag、failed events、reconcile pending items、assignment lease 状态指标。
- standby 复制链路中 generation mismatch、sequence conflict、assignment 失效等关键错误的结构化日志。
- active / standby 心跳过期告警。
- reconcile 失败与长期未完成告警。
- `ha status` 输出补充 generation / assignment / reconcile 状态解释字段。

验收标准：

- 不看数据库明细，也能通过日志、状态接口、指标快速定位复制链路问题。
- 故障切换前有清晰检查项，切换后有清晰回滚路径。

### 多 Standby Reconcile 并发与限流

目标是在已经支持 `1 active -> N standby` 的基础上，补齐并发控制、带宽限制和资源保护。

- 多 standby 下的 reconcile 并发数控制。
- 单 standby 与全局带宽限流。
- active 本机资源保护策略，避免 reconcile 抢占正常写流量。
- 单个 standby 异常时的资源隔离与退避策略。

验收标准：

- 多个 standby 同时补历史时，不会明显拖垮 active 正常服务。
- 单个 standby 的慢或失败，不会放大成全局抖动。

### Generation 生命周期清理

generation 已经严格生效后，必须补上历史代际数据的生命周期管理。

- 为 `replication_outbox` 增加旧 generation 清理策略。
- 为 `replication_reconcile_jobs` / `replication_reconcile_items` 增加保留期与清理策略。
- 明确 `replication_offsets` 在 assignment 释放或切换后的保留策略。
- 明确 `cluster_replication_assignments` 的 released / expired 记录是否归档或裁剪。
- 设计人工触发与自动清理两种方式。

验收标准：

- 长期运行后数据库不会因为历史 generation 累积而无限膨胀。
- 清理策略不影响当前有效 assignment、reconcile 和 outbox apply。

### Quota 运维基础版

当前 quota 基线见 [额度管理方案.md](./额度管理方案.md)。V2 只保留运维必要项，不做完整额度产品化。

- quota 对账任务分片扫描、限速、失败记录和结构化告警。
- 管理端额度视图，支持识别接近上限、已超额和统计可能漂移的用户。
- 目录级 `COPY` / 目录树复制的高性能 quota 估算，避免大目录复制时反复递归扫描。

验收标准：

- 大目录复制和大规模对账不会拖垮 active 正常读写。
- 管理员不查数据库也能定位用户超额、统计漂移和对账失败。
- quota 仍只在 active 对外写入口判定，standby 不因副本同步重复拒绝或重复计量。

### WebDAV 系统对象生命周期治理

目标是让用户文件和系统同步对象的生命周期边界清晰，避免内部对象污染用户回收站。

- 设计受限硬删除接口，供 chat 等内部应用显式清理同步内部对象。
- 为硬删除接口补充能力校验或内部认证边界，避免普通客户端绕过回收站。
- 梳理并固化可硬删除的系统对象范围，减少散落的路径特判。
- 增加历史 `.recycle` 中 `__sync_*` 系统对象的识别与清理脚本。

验收标准：

- 用户文件删除仍默认进入回收站。
- 系统同步对象具备受控、可审计、不会污染回收站的清理路径。

## V2 不做

以下内容不进入 V2，统一放到 [仓库架构V3.md](./仓库架构V3.md) 或更后版本：

- 正式多副本 / 无状态应用副本。
- WebDAV lock、challenge、邮箱验证码、上传会话等完整状态外置。
- 自动 failover / promote / rebalance / drain / release 编排。
- 完整运维 CLI 平台化。
- quota 自助扩容、套餐/计费、多主体额度、强 reservation 状态机。
- 完整逻辑文件元数据表。
- 大文件流式 reconcile、复制批量大小自适应、深度性能优化。
- Agent Run、Context Manifest、Service Principal、Artifact Provenance 控制面。

## V2 建议执行顺序

1. 先固化 Warehouse 支撑 Knowledge 的数据源与反馈资产边界。
2. 再补 reconcile 调度与自愈。
3. 接着补复制观测、告警、`ha status` 和 generation 生命周期管理。
4. 再补多 standby reconcile 并发与限流。
5. 补 quota 运维基础版和 WebDAV 系统对象生命周期治理。
6. 最后整理 manual failover SOP，为 V3 自动编排铺路。

## V2 完成标准

V2 完成时，Warehouse 应满足：

- 能作为 Knowledge 的稳定数据源和反馈资产回写层。
- standby 中断后能自动恢复或进入可操作失败状态。
- 复制链路、quota 对账和系统对象清理具备基本观测和运维入口。
- 多 standby 补历史不会拖垮 active。
- 文档和部署手册只维护一套运维命令。
