# Warehouse S3 设计方案

本文档描述 Warehouse S3 兼容能力的当前设计与实际实现，包括系统定位、协议能力、凭证与目录授权、数据写入、安全边界、部署方式和已知限制。文档内容以当前代码和已完成验证为准；未来规划仅概括可能的演进方向，不作为当前能力承诺。

普通用户配置 AWS CLI、rclone 和 MinIO Client 时，请优先阅读 [用户使用指南](./用户使用指南.md#4-s3-凭证使用)。S3 凭证管理 JSON API 以 [OpenAPI](./openapi/warehouse.openapi.yaml) 为准。

## 1. 当前定位

Warehouse 已实现可使用的 S3 兼容协议层，用于让 AWS CLI、AWS SDK、rclone、MinIO Client 等工具访问 Warehouse 中的文件。

它不代表底层存储已迁移到 AWS S3 或 MinIO：

```text
S3 Client
   |
   | AWS Signature V4 + S3 HTTP/XML
   v
Warehouse S3 Server
   |
   v
ObjectService / MultipartService
   |
   +-- 本地文件目录
   +-- PostgreSQL 元数据、凭证、Multipart 状态
   +-- 配额、原子写入和 active/standby 复制链路
```

WebDAV、Web 页面和 S3 看到的 `personal` / `apps` / `services` 是同一份用户数据。

## 2. Endpoint 与配置

生产 Endpoint：

```text
https://s3.tidukongjian.com
```

当前推荐 path-style 访问：

```text
https://s3.tidukongjian.com/{bucket}/{key}
```

例如：

```text
https://s3.tidukongjian.com/personal/backup/report.zip
```

核心服务端配置：

```yaml
s3:
  enabled: true
  address: "127.0.0.1"
  port: 6066
  tls: false
  region: "us-east-1"
  read_timeout: 5m
  write_timeout: 5m
  idle_timeout: 60s
  shutdown_timeout: 10s
```

部署环境可使用 `WAREHOUSE_S3_ENABLED` 覆盖 YAML 中的启用状态。S3 Secret 加密主密钥只通过环境变量提供：

```text
WAREHOUSE_S3_CREDENTIAL_MASTER_KEY
```

该密钥必须在重启、发布和 active/standby 切换后保持一致，否则已创建的 S3 Secret 无法解密验签。

## 3. 逻辑 Bucket

当前固定开放三个逻辑 bucket：

| Bucket | 对应资产空间 | 说明 |
| --- | --- | --- |
| `personal` | `/personal` | 个人资产 |
| `apps` | `/apps` | 应用资产 |
| `services` | `/services` | 服务资产 |

Bucket 是当前认证用户下的逻辑视图，不是全局用户共享的物理 bucket。

`ListBuckets` 只返回当前 S3 凭证可见的 bucket。对三个固定 bucket 执行 `CreateBucket` 会幂等成功，用于兼容 rclone 等上传前自动创建 bucket 的客户端；不允许创建任意 bucket。

## 4. S3 凭证与目录范围

S3 凭证使用独立的 Access Key ID 和 Secret，通过 AWS Signature V4 验证。WebDAV Basic 密钥与 S3 凭证不能互用。

凭证支持：

- 独立名称。
- `read` / `create` / `update` / `delete` 权限。
- 撤销后再删除。
- 限制到 bucket 或 bucket 下的 Object Key prefix。

例如 Warehouse 凭证的 `rootPath` 是：

```text
/personal/backup
```

第三方 S3 客户端应使用：

```text
Bucket: personal
Prefix: backup/
```

`rootPath` 是 Warehouse 的服务端授权字段，不是 S3 标准凭证字段。客户端仍使用标准 bucket/key 请求，Warehouse 在服务端对 prefix 执行权限检查。

## 6. 写入、校验和元数据

PutObject 和 Multipart 不由 S3 Handler 直接写最终文件，而是复用 ObjectService / MultipartService：

- 临时文件或 staging 分片写入。
- 配额检查和 Multipart staging 预留。
- 同步计算 MD5 / SHA-256。
- 校验 `Content-MD5`、`x-amz-checksum-sha256`、`x-amz-checksum-crc32`。
- 原子替换最终文件。
- 记录复制变更。
- 保存对象 ETag 和 Content-Type 元数据。

S3 单次上传产生稳定 ETag。Multipart 完成后使用标准形式的 Multipart ETag：

```text
<combined-md5>-<part-count>
```

WebDAV 或文件系统中已存在但没有 S3 元数据的文件，使用可重复计算的 fallback ETag。

## 7. Multipart 限制

当前代码限制：

| 项目 | 限制 |
| --- | --- |
| 非最后分片最小值 | 5 MiB |
| 单分片最大值 | 5 GiB |
| Multipart 对象最大值 | 100 GiB |

Multipart 会话与分片状态保存在 PostgreSQL，分片内容保存在不可通过 WebDAV/S3 列出的 staging 目录。后台任务会清理过期会话。

## 8. Signature V4 与安全边界

当前验签器支持：

- Authorization Header 形式的 AWS Signature V4。
- 固定 service `s3`。
- 按 `s3.region` 校验 region。
- Canonical URI、Canonical Query、SignedHeaders 和 payload hash。
- aws-chunked streaming signature。
- HTTPS 或可信反向代理标记下的 `UNSIGNED-PAYLOAD`。

所有 bucket/key 会进入统一路径解析，防止 `..`、编码绕过和逃出用户资产根目录。权限同时检查：

```text
凭证状态 + 凭证 rootPath + CRUD 权限 + bucket/key
```

## 9. 删除语义

S3 `DeleteObject` 和 `DeleteObjects` 使用永久删除，不进入 Warehouse 回收站。

这是为了符合 S3 客户端对删除和配额释放的预期。Web 页面和 WebDAV 删除仍可继续使用 Warehouse 回收站语义。

S3 与 WebDAV、Web 页面操作的是同一套用户资产，因此 S3 删除成功后，服务端还会删除该对象对应的定向分享、公开链接以及从定向分享派生的公开链接。`DeleteObjects` 对每个成功删除的对象执行相同处理，避免文件已经不存在但分享列表仍保留悬空记录。

创建 S3 凭证时应将这一行为明确风险提示展示给用户。

## 10. active/standby 与一致性

- 对外 S3 流量只进入 active。
- S3 写入复用 MutationRecorder，进入现有 active/standby 复制链路。
- S3 凭证、Multipart 状态和对象元数据保存在 PostgreSQL。
- 新 active 必须获得同一 S3 凭证主密钥。
- 对外成功表示 active 本地写入和必要元数据处理已完成，不表示所有 standby 都已同步落盘。

## 11. 已验证客户端

开发与回归过程中已验证：

| 客户端 | 验证内容 |
| --- | --- |
| AWS SDK for Go | Signature V4、PutObject 请求、checksum 行为 |
| AWS CLI `1.45.45` | ListBuckets、ListObjectsV2、PutObject、GetObject |
| rclone `1.74.4` | ListBuckets、ListObjects v1、CreateBucket、PutObject、GetObject |
| Go 反向代理验证 | Host、URI、Query、Authorization 和 `X-Amz-*` 签名语义保留 |

rclone 默认使用 ListObjects v1，并可能在上传前调用 CreateBucket；当前实现已兼容这些行为。

## 12. 当前未支持或不承诺的能力

以下不属于当前已实现契约：

- 创建 `personal` / `apps` / `services` 以外的任意 bucket。
- DeleteBucket。
- CopyObject 和 UploadPartCopy。
- ListParts 和 ListMultipartUploads。
- Bucket ACL、Object ACL、Bucket Policy 和 IAM API。
- Object Versioning、Object Lock 和 Lifecycle Rule。
- SSE-S3、SSE-KMS 和 SSE-C。
- Presigned URL 作为明确对外兼容承诺。
- `share-{shareId}` 或“分享给我的” S3 bucket。
- AWS S3 全部错误码、请求头和扩展元数据的完整兼容。
- Virtual-hosted-style 作为默认推荐方式。

未实现的操作应返回 S3 XML 错误，通常为 `NotImplemented`。

## 13. 已知运行边界

- 某些第三方应用只能配置 bucket，不能配置 key prefix；这类应用应使用整个 bucket 范围的凭证。
- 客户端使用 CopyObject + DeleteObject 模拟 rename 时，当前会因 CopyObject 未实现而失败。
- 依赖任意 `x-amz-meta-*` 持久化的 S3 原生应用不应默认认为完全兼容。
- 生产反向代理不能重写已参与签名的 Host、URI、Query 或 `X-Amz-*` 头语义。
- `UNSIGNED-PAYLOAD` 只应在直接 TLS 或明确可信的 HTTPS 反向代理链路中接受。

## 14. 未来规划

S3 功能已经具备当前生产接入所需的核心能力。后续演进将以真实客户端需求、生产运行数据和安全要求为依据，主要关注以下方向：

- 协议兼容：逐步补充 CopyObject、Multipart 查询、Presigned URL、扩展元数据和更完整的 S3 错误语义。
- 产品体验：完善凭证创建与接入指引，提供 Endpoint、Region、Bucket、Prefix 和常用客户端配置示例，并评估分享空间的 S3 映射方式。
- 安全审计：根据需要增加凭证有效期、最近使用时间、操作审计和更细粒度的风险提示。
- 运维观测：完善请求延迟、传输流量、签名失败、配额拒绝、Multipart staging 和清理任务等指标与告警。
- 兼容验证：持续覆盖 AWS CLI、AWS SDK、rclone、mc 以及真实 Nginx/TLS 代理链路。
- 一致性与容灾：加强 Multipart、对象元数据、复制记录和 active/standby 切换场景的故障验证、对账与自愈能力。

上述内容是方向性规划，不表示对应功能已经实现，也不构成版本或交付时间承诺。当前支持范围应以本文第 5、12、13 节和实际发布版本为准。

## 15. 验收建议

每次修改 S3 协议层后，至少执行：

```bash
go test ./internal/interface/s3/...
go test ./internal/application/service/...
go test ./internal/infrastructure/repository/...
go test ./...
```

生产发布前建议使用真实 Endpoint 完成：

- AWS CLI 列桶、列对象、上传、下载和删除。
- rclone 列表、同步、覆盖和删除。
- mc 连接、上传、下载和批量删除。
- 小文件 PutObject 和大文件 Multipart Upload。
- prefix 范围凭证对范围外 key 返回 `AccessDenied`。
- active/standby 复制和切换后读取。
