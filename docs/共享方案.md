# 共享方案

本文统一描述 Warehouse 公开分享、站内共享的当前实现、运行流程和后续演进方向。

目标是解决下面三个问题：

- 当前“单地址定向分享”体验偏重，批量分享成本高
- 目录共享虽然已有基础能力，但还没有成为主路径
- 一部分资产需要直接面向全体已登录用户共享

## 文档边界

本文讨论公开分享和站内共享，重点是共享对象、受众模型、分组语义、全员共享及资源路径变更时的处理。

以下内容不在本文重复展开：

- 个人资产 / 应用资产目录如何分层：见 [资产空间分层方案.md](./资产空间分层方案.md)
- 回收站行为：见 [仓库架构V1.md](./仓库架构V1.md)
- 具体接口字段：见 [Warehouse OpenAPI](./openapi/README.md)

## 1. 当前现状

当前代码里有两套分享模型：

- 外链分享：`share_items`
  - 面向公开链接访问
  - 当前只支持文件，不支持目录
- 站内共享：`internal_share_items + internal_share_audiences`
  - 面向站内已登录用户
  - 已支持文件或目录
  - 已支持 `read/create/update/delete` 权限

旧库中的 `share_user_items` 会在升级时幂等迁移到统一站内共享模型。

当前前后端已经落地统一“站内共享创建”语义：

- `targetMode=addresses`：使用 `targetAddresses`，可传多个地址
- `targetMode=groups`：使用 `groupIds`，可传多个分组
- `targetMode=all_users`：共享给所有已登录用户
- 统一调用 `share/user/create`；指定地址会去重，分组保存为 `group` audience，并按当前有效成员动态授权

这说明产品方向已经从“多条单用户分享记录”演进到“单条共享对象 + 多受众”模型。

### 1.1 公开分享运行流程

- 公开分享使用 `share_items` 保存 token、资源路径和有效期。
- 当前仅支持文件，不支持目录；`expiresIn > 0` 时生成过期时间。
- 访问入口为 `GET /api/v1/public/share/{token}`，解析 token 后读取文件。
- `Range` 非首段请求不会重复增加查看或下载计数，避免分片下载造成统计膨胀。

### 1.2 站内共享运行事实

- 目标用户通过钱包地址匹配。
- `permissions` 支持 `read/create/update/delete`，也兼容对应 `CRUD` 表达。
- 文件和目录均可共享。
- 浏览、下载、上传、创建目录、重命名和删除都会校验对应权限位。
- 公开链接仍保存在 `share_items`；由收到的站内共享派生出的公开链接通过 `source_share_id` 关联来源共享，资源所有者仍记录在 `user_id`。

### 1.3 资源删除、移动与引用维护

共享当前仍是路径型引用。资源通过 Warehouse 支持的写入口删除、移动或重命名时，服务端统一维护站内共享和公开链接：

- 删除文件或目录时，删除根路径及目录下子路径的共享引用和派生公开链接。
- 路径匹配遵循完整目录边界；删除 `/personal/snmp` 不影响 `/personal/snmp_backup`。
- 移动或重命名时，更新根资源及子路径的共享路径；根资源改名时同步更新显示名称。
- WebDAV `DELETE/MOVE`、S3 `DeleteObject/DeleteObjects`、收到的共享 WebDAV 操作及站内共享文件操作接口均进入统一处理。
- `COPY` 不改变源资源共享，新副本不继承共享；覆盖上传因逻辑路径不变而保留共享。

文件系统和 PostgreSQL 共享元数据目前不是跨存储事务。绕过 Warehouse 直接修改文件系统时仍可能产生悬空引用，需要通过撤销或后续对账清理。

### 1.4 升级与 standby

- 旧库中的 `share_user_items` 会在启动时幂等导入 `internal_share_items/internal_share_audiences`。
- 创建接口只接受 `targetMode + targetAddresses/groupIds`，不再兼容旧 `targetAddress`。
- 共享元数据保存在 PostgreSQL；active/standby 共享数据库时可读取同一份元数据。
- 共享目录内的文件变更继续通过复制 outbox / internal replication 同步到 standby。

## 2. 当前问题

### 2.1 单地址共享仍是能力，但不再是主模型

旧模型是“一个路径 -> 一个目标地址 -> 一条分享记录”，会产生重复记录和批量维护问题。当前已经迁移到“一个共享对象 + 多个受众”，单地址共享只是 `user` audience 的特例。后续重点是完善受众编辑、统一撤销和列表聚合体验，而不是恢复旧模型。

### 2.2 动态分组授权需要明确治理边界

当前分组以 `group` audience 保存，访问时按分组当前有效成员动态授权：加入分组后获得访问权，离开或被移除后失去访问权。这个模型已经落地，但仍需继续补充成员变化审计、用户提示和高风险权限确认，避免管理员调整成员时产生难以察觉的权限变化。

### 2.3 “面向所有用户共享”不等于“公开链接”

“所有用户共享”和“公开分享链接”是两种完全不同的能力：

- 公开链接：知道链接即可访问，偏向站外分发
- 所有用户共享：必须登录系统，偏向站内公共资源

如果把“所有用户共享”做成公开链接，会带来这些问题：

- 权限边界过粗
- 审计困难
- 撤销和管理不清晰
- 产品心智混乱

所以“所有用户共享”应属于站内共享的一种 audience，而不是公开链接的变体。

### 2.4 目录共享已经有基础，但产品主路径还不够明确

当前定向分享已经支持目录，但从产品形态看，目录共享还没有成为默认主路径，用户仍然更容易把分享理解成“给一个地址发一个对象”。

后续如果要提升体验，应该反过来：

- 把目录共享作为主路径
- 单文件共享作为轻量特例

### 2.5 当前分享是路径型绑定，目录变更会影响体验

当前分享本质上仍是“路径型引用”，不是独立对象引用。服务端已经在 WebDAV、S3 和定向分享文件操作等受支持的删除、移动入口中，统一维护定向分享与公开链接引用：删除资源会撤销根路径及子路径分享，移动或重命名会迁移相应路径。

这个设计在当前阶段是可以接受的，但在做目录共享和公共资源时，需要在产品说明里明确边界：

- 被分享根路径删除后，共享及其派生公开链接随之失效
- 通过受支持入口移动或重命名时，分享引用会跟随新路径
- `COPY` 不自动复制分享关系
- 绕过 Warehouse 直接修改底层文件系统时，仍可能产生无法实时处理的悬空引用
- 后续若要让分享完全脱离路径变化，需要引入稳定资源标识，并增加历史悬空引用对账能力

当前阶段继续使用路径型引用，未来再结合对象元数据模型评估稳定资源标识。

## 3. 推荐路线

推荐把分享能力明确拆成两条产品线：

### 3.1 外链分享

定位：

- 面向匿名或站外访问
- 保留 token / URL 形式
- 继续用于“发一个链接出去”

建议：

- 保留当前 `share_items`
- 短期内继续保持“只支持文件”
- 不把“全员共享”塞进这条模型里

### 3.2 站内共享

定位：

- 面向已登录用户
- 支持文件与目录
- 支持权限控制
- 支持单用户、分组、全员三种受众

建议：

- 让“单地址共享”成为“站内共享”的一个特例
- 让“分组共享”成为“站内共享”的主增强点
- 让“所有用户共享”成为“站内共享”的内建 audience

一句话概括：

- 外链分享解决“发链接”
- 站内共享解决“协作和分发”

## 4. 当前数据模型

当前已经使用“共享对象”和“共享受众”两层结构；`share_user_items` 仅作为历史迁移来源。

### 4.1 已落地模型

#### `internal_share_items`

表示“一次站内共享本身”。

主要字段：

- `id`
- `owner_user_id`
- `owner_username`
- `path`
- `name`
- `is_dir`
- `permissions`
- `expires_at`
- `status`
- `created_at`
- `updated_at`

说明：

- `path` 仍然沿用当前路径型模型，先不引入复杂对象引用
- `permissions` 先继续复用当前权限编码方式
- `status` 可先只保留 `active` / `revoked`

#### `internal_share_audiences`

表示“一次站内共享到底发给谁”。

建议字段：

- `id`
- `share_id`
- `audience_type`
- `target_user_id`
- `target_wallet_address`
- `source_group_id`
- `created_at`

其中：

- `audience_type` 取值建议为：
  - `user`
  - `group`
  - `all_users`
- `user` 使用目标用户和钱包字段。
- `group` 使用 `source_group_id`，访问时动态查询当前有效成员。
- `all_users` 不需要目标用户或分组引用。

### 4.2 为什么推荐拆成两层

因为“共享对象”和“共享对象的受众”不是一个维度：

- 共享对象关心的是：
  - 共享什么
  - 谁创建的
  - 权限和有效期是什么
- 受众关心的是：
  - 这份共享到底给谁看
  - 是用户、分组还是全员

拆开后才能自然支持：

- 一次共享对应多个受众
- 一处改权限，多个受众一起生效
- 一次撤销整个共享，而不是删一堆重复记录
- 后续加审计、备注、标签、排序更容易

### 4.3 分组语义

分组是动态 ACL 受众，不是创建时的一次性成员快照：

- 创建共享时保存 `group` audience。
- 当前有效成员可以访问共享。
- 后续加入分组的成员自动获得访问权。
- 离开分组或被移除的成员自动失去访问权。
- 创建时解析出的用户仅用于通知等辅助流程，不作为长期授权事实。

### 4.4 关于“所有用户共享”

建议作为 `audience_type = all_users` 的内建受众。

这样设计的好处是：

- 权限边界清晰，必须登录才能访问
- 可以和单用户/分组共享共用同一套站内共享机制
- 后续可以单独提供“公共资源”入口，而不是复用外链

## 5. API 草案

### 5.1 设计原则

- 浏览、下载、上传、重命名、删除等运行时接口，尽量复用现有 `share/user` 访问模型
- 变化重点放在“创建 / 列表 / 受众管理”层
- 迁移兼容以“数据回填 + 路径不变”为主，不再保留旧 `targetAddress` 单字段调用兼容

### 5.2 推荐新接口

#### 创建站内共享

`POST /api/v1/public/share/internal/create`

请求示例：

```json
{
  "path": "/docs/project-a",
  "permissions": ["read", "update"],
  "expiresValue": 2,
  "expiresUnit": "week",
  "audiences": [
    { "type": "user", "userId": "u-1" },
    { "type": "user", "walletAddress": "0xabc..." },
    { "type": "groups", "groupIds": ["g-1", "g-2"] },
    { "type": "all_users" }
  ]
}
```

返回示例：

```json
{
  "id": "share-internal-id",
  "name": "project-a",
  "path": "/docs/project-a",
  "isDir": true,
  "permissions": ["read", "update"],
  "expiresAt": "2026-03-31T12:00:00Z",
  "audienceSummary": {
    "userCount": 3,
    "groupCount": 1,
    "allUsers": false
  }
}
```

#### 我发起的站内共享列表

`GET /api/v1/public/share/internal/list?view=owned`

用途：

- 展示我发起的共享对象
- 一条共享对象只显示一行
- 详情中再展开受众信息

#### 分享给我的站内共享列表

`GET /api/v1/public/share/internal/list?view=received`

用途：

- 返回当前用户通过 `user` / `groups` / `all_users` 获得访问权的共享对象

#### 公共资源列表

`GET /api/v1/public/share/internal/list?view=public`

用途：

- 专门列出 `all_users` 类型的共享对象
- 后续可以加标签、搜索、排序、置顶

#### 查看共享受众详情

`GET /api/v1/public/share/internal/audiences?shareId=...`

用途：

- 给拥有者查看这份共享发给了谁
- 支持后续按受众单独撤销

#### 更新共享受众

`PUT /api/v1/public/share/internal/audiences`

请求示例：

```json
{
  "shareId": "share-internal-id",
  "add": [
    { "type": "user", "walletAddress": "0xdef..." },
    { "type": "groups", "groupIds": ["g-2"] }
  ],
  "remove": [
    { "type": "user", "userId": "u-1" }
  ]
}
```

#### 撤销整条站内共享

`POST /api/v1/public/share/internal/revoke`

请求示例：

```json
{ "shareId": "share-internal-id" }
```

### 5.3 兼容策略

现有接口：

- `POST /api/v1/public/share/user/create`
- `GET /api/v1/public/share/user/list`
- `GET /api/v1/public/share/user/received`
- `POST /api/v1/public/share/user/revoke`

当前兼容策略（已落地）：

- 路径保持 `share/user/*` 不变，避免部署和路由层改动
- 创建请求体统一使用新契约：`targetMode + targetAddresses/groupIds`
- 不再兼容旧 `targetAddress` 单字段调用
- 启动迁移会幂等回填 `share_user_items -> internal_share_items/internal_share_audiences`

## 6. 前端交互建议

### 6.1 顶层入口

建议把当前“下载链接 / 定向分享”两个入口调整为：

- `外链分享`
- `站内共享`

这样命名更符合用户认知。

### 6.2 创建站内共享弹窗

建议统一成一套“共享给谁 + 对方能做什么”的表单。

表单建议：

- 共享对象
  - 文件
  - 目录
- 共享范围
  - 指定用户
  - 共享分组
  - 所有用户
- 权限预设
  - 只读
  - 可上传
  - 可编辑
  - 完全协作
- 有效期
  - 沿用当前分钟/小时/天/周/月/年

说明：

- “指定用户”和“共享分组”应支持多选
- “所有用户”建议单独作为显式选项，不和分组管理混在一起

### 6.3 列表信息架构

站内共享建议拆成三个子视图：

- `我发起的`
- `分享给我的`
- `公共资源`

这样可以避免把“别人分享给我”和“全员共享”混在一个列表里。

### 6.4 详情页建议

对于我发起的站内共享，详情页建议显示：

- 共享根路径
- 是否目录
- 权限
- 过期时间
- 受众摘要
- 受众明细

对于“公共资源”，建议额外支持：

- 简介
- 标签
- 置顶
- 最近更新时间

否则“所有用户共享”很快会退化成难以查找的大列表。

## 7. 后续演进顺序

统一站内共享模型、单用户/动态分组/全员受众和旧数据迁移已经完成。下一阶段重点是产品体验与治理能力：

目标：

- 补更强的组织化共享、审计和公共空间运营能力

可选动作：

- 分组成员变化审计和高风险权限提示
- 受众编辑与按受众撤销
- 公共资源标签、搜索、置顶、排序
- 审计日志和访问统计增强
- 稳定资源标识与悬空路径引用对账

这些能力按真实协作需求逐步验证，不重新引入旧 `share_user_items` 模型。

## 8. 明确的推荐与不推荐

### 8.1 推荐

- 保留“外链分享”和“站内共享”两条产品线
- 让目录共享成为站内共享主路径
- 让单地址共享退化成站内共享的一个特例
- 保持分组按当前有效成员动态授权，并补齐成员变化审计
- 把“所有用户共享”建模成 `all_users` audience

### 8.2 不推荐

- 不推荐把“所有用户共享”直接做成公开链接
- 不推荐恢复 `share_user_items` 或继续围绕旧表叠加例外逻辑
- 不推荐把创建时解析出的成员快照作为长期分组授权事实
- 不推荐一开始就解决“路径重命名后共享仍然稳定”这种高复杂度问题

## 9. 结合当前代码的具体判断

统一共享对象、多受众和动态分组授权已经落地。下一步建议优先做：

1. 在产品上把“目录站内共享”提升为主入口
2. 完善单用户、分组、全员受众的详情编辑和撤销体验
3. 增加分组成员变化审计、公共资源检索和悬空引用对账

这样做的原因是：

- 它建立在当前统一共享模型上
- 它能覆盖你提出的三个核心诉求
- 它不会把“外链分享”和“站内共享”继续混在一起
- 它给后续公共资源空间、团队分发和权限治理留下了清晰演进路径

## 10. V3 共享资源 / 授权分离

本章是 [仓库架构V3.md](./仓库架构V3.md#平台化共享资源与授权治理) 的专项设计，用于解决“同一目录多次分享给我，接收列表出现多行”的问题。

### 10.1 不是一个简单去重问题

列表不能按 `name` 或 `path` 去重。不同 owner 可以拥有同名、同路径的不同资源；同一 owner 对同资源又可以给不同受众配置不同权限和有效期。

因此，V3 的资源聚合键为：

```text
(owner_user_id, normalized_path, is_dir)
```

不同 owner 的同名资源保持为独立行；同一 owner 的同一资源聚合为一行。

### 10.2 目标数据模型

| 层 | 表 | 责任 |
| --- | --- | --- |
| 资源 | `internal_shared_resources` | 唯一标识 owner 下被共享的文件或目录 |
| 授权 | `internal_share_grants` | 保存一组权限、有效期、状态和审计字段 |
| 受众 | `internal_share_audiences` | 将用户、分组、全员绑定到 grant |

`internal_share_items` 不再继续演进为一个既表示资源又表示权限的表；迁移后它的每条活跃记录对应一条 grant。

`normalized_path` 必须由后端使用唯一的路径规范化逻辑生成，拒绝由客户端传入或仅做字符串比较。

### 10.3 列表、详情与操作权限

“分享给我的”默认返回 resource rows，其中包括所有效 grants 的数量、授权来源概要、可读/可写状态和详情入口。一个 resource row 不等于一条 grant：

- 列表可以展示有效 grants 的权限概要。
- 详情页必须列出每条 grant 的权限、有效期和受众来源。
- 读、上传、创建、更新、移动、删除等请求都按 resource 重新解析 effective grant，不使用前端计算的权限并集作为授权依据。
- 后端对每个动作判定“是否存在任一条满足该动作的有效 grant”。

这使下列情况不会造成越权：

```text
grant A: read，永不过期
grant B: update，30 天后过期
```

列表可以显示“可读、可编辑”，但 30 天后任何写操作必须被后端拒绝，因为剩余的 grant 只允许 read。

第一步将授权语义固化为独立的 effective-grant 领域能力：只统计 `active` 且未过期的 grants；列表展示可以使用它们的权限并集，但每次实际操作均重新按所需 CRUD action 求值。旧数据中空权限串沿用既有“默认只读”语义。

### 10.4 迁移和兼容策略

1. 先增加新表和索引，不修改现有读写路径。
2. 回填资源和 grant，同一 owner/path/type 的旧记录挂载到同一 resource。
3. audience 从旧 share item 关联迁移到 grant 关联，分组仍在访问时动态解析成员。
4. 将后端授权、收件列表、目录浏览、创建目录、上传、在线文本编辑、重命名、删除和移动切到新模型；尚未有 resource API 的操作显式禁用，不能回落到旧 `shareId`。
5. 完成数据对账和生产回归后，再按 owner 管理路径的迁移进度删除旧表依赖。

迁移过程不按名称合并，不改变历史 grant 的 permissions、expires_at、status 或 audience。

### 10.5 接收端交互

默认行应显示资源，不显示分享记录：

| 名称 | 分享人 | 权限概要 | 有效授权 | 操作 |
| --- | --- | --- | --- | --- |
| 夜莺社区公开资料 | 张三 | 可读、可编辑 | 2 个授权 | 打开 / 详情 |

当前详情展示资源所有者、权限并集和有效 grant 数；逐 grant 的受众、有效期和权限审计视图仍是后续治理界面的工作，且不能影响 resource 级授权的正确性。

### 10.6 实施顺序与验收

1. 已完成 schema、旧数据回填工具与 resource/grant/audience 对账。
2. 已完成 effective-grant 授权服务；上传会话（包括在线文本编辑）按 `C` / `U` 重新鉴权，目录浏览、下载、创建目录、重命名、删除和移动也已使用 resource ID；移动/删除会立即同步受影响的 resource 元数据，不等待开机 reconcile。
3. 已切换接收列表为资源聚合视图，显示权限并集和有效 grant 数；同资源不再返回多行。
4. 二次创建公开链接没有安全的 resource-scoped 授权生命周期语义，legacy 接口已移除；owner 管理和旧表下线是后续独立迁移。

核心验收：同一资源多次授权在接收端只显示一行，但任意一条 grant 的过期、撤销或权限变更都不影响其他 grant 的独立语义。
